# COOLForge — technical report

## Problem and intended users

Computer-vision engineers often reduce latency by resizing frames or simplifying
filtering. Those changes can remove the very defects an inspection system needs to
detect. Manual experimentation also makes it easy to compare different inputs,
threads, or library builds and misattribute a speedup. COOLForge couples performance
experiments to foreground correctness, provenance, and a reviewable decision trail.

The intended users are developers evaluating material/surface inspection pipelines
and teams assessing whether a specialized OpenCV build benefits their workload.
This prototype is not an industrial inspection product or a trained defect classifier.

## Implemented system

The [architecture](docs/ARCHITECTURE.md) contains the agent and AWS diagrams. The core
is a typed Python package with a four-tab Streamlit workbench, deterministic data,
an auditable optimization policy, interpreter-isolated benchmarks, and deployment assets.
There is no external LLM API, database, training job, or required MCP server.

The substantive OpenCV workload resizes BGR images, converts to grayscale, performs
Gaussian blur, adaptive Gaussian inverse thresholding, morphological opening, contour
extraction/filtering, binary mask reconstruction, and annotated bounding boxes. Minimum
area is interpreted in original-image coordinates. Every candidate runs these operations;
the agent does not merely describe an already computed result.

The implementation uses APIs intended for the OpenCV 5 target. Local development was
executed with OpenCV 4.13. That confirms local behavior only: final OpenCV 5 execution
has not been observed here and is a required operator validation step.

## Agentic behavior and human control

Each iteration observes measured precision/recall/F1/IoU and latency, selects a valid
one-coordinate mutation, invokes OpenCV, evaluates the new output, and accepts or rolls
back. Prior candidate recall loss changes the next decision branch. False positives
prioritize suppression; feasible quality permits cheaper scale experiments. Tests inject
controlled observations to prove that changing visual evidence changes the next action.

The default policy requires F1 ≥ 0.85 and either a 3% p50 improvement or a quality gain
above 0.005 within a 2% latency allowance. These are configurable experimental choices,
not calibrated industrial guarantees. Each trace stores observation, action, rationale,
config, result, acceptance, and failure. Search is bounded and deduplicates configurations.

The UI compares the incumbent and proposal, evaluates both on 20 held-out surfaces
(seed 1042), reruns the selected pipeline for a live preview, and enables approval/export
only if tuning and held-out quality meet the floor. Changing controls invalidates the
review. Export is a human action and does not change a deployed workload.

## Data and metrics

The default dataset contains 50 synthetic 384 × 256 surfaces at seed 42, evenly cycling
through clean, scratch, crack, pit, and irregular-blob cases. Illumination gradients,
periodic texture, and Gaussian noise vary backgrounds. Each mask is the exact raster
support whose intensity was reduced. This is not a real-world generalization study.

Primary quality is micro pixel F1, obtained from summed TP/FP/FN, accompanied by
precision, recall, IoU, and macro per-image F1. Empty/empty masks score F1/IoU 1;
missed positives and false detections are handled without division by zero. Background
accuracy is not used. A failed image invalidates the candidate rather than disappearing
from the denominator.

Latency uses a monotonic nanosecond clock across seven stages. Reports include mean,
p50, p95, and reciprocal-mean sequential throughput. Annotation is included; disk I/O,
metric calculation, UI rendering, and dataset generation are excluded. Warmups are per
image, followed by repeated measurements in manifest order.

## Actual local evidence

The checked-in [measurement summary](docs/assets/LOCAL_RESULTS.md),
[benchmark artifact](docs/assets/local-benchmark.json), and
[agent/hold-out artifact](docs/assets/local-agent.json) were generated by actual local
execution. The summary is generated from those artifacts instead of hand-entered claims.
The dataset's default foreground F1 is approximately 0.941 on this local build. That
number is synthetic segmentation quality; it is not a production detection rate.

The agent trace includes multi-step OpenCV execution, candidate rejection, and final
selection. The synthetic contact sheet exposes common oversegmentation around thin
defects. Browser screenshots are from a separate real interactive run, so their one-shot
latencies can differ. No fixture is presented as a measurement. Regenerate with:

```bash
python scripts/export_demo.py
python -m pytest -q
python -m ruff check .
python -m ruff format --check .
```

Automated tests cover invalid config, serialization, mask metrics, seeds, dataset
integrity, pipeline outputs, failed samples, adaptive decisions, rollback, budget stops,
weak COOL evidence, benchmark mismatches, CLI processes, and app review state.
Timing assertions are not used to fabricate stable performance outcomes.

## COOL integration and AWS component

The intended meaningful AWS component is the actual inspection and optimization workload
on an official COOL Marketplace Arm AMI. Streamlit runs under the vendor interpreter
and Nginx fronts localhost. A systemd unit provides a persistent unprivileged process.
The installer never installs another OpenCV wheel into the vendor environment.

The verifier requires OpenCV 5, Arm64, installation-root presence, loaded `cv2` provenance,
and affirmative backend markers. SVE or a directory alone cannot pass. This establishes
build provenance, not individual kernel dispatch or AWS hosting. Save instance type,
AMI release, COOL version, and CPU details with the run. See [deployment](deploy/aws/README.md).

## Failure cases and limitations

- Thin cracks can vanish at small scales or after morphological opening.
- Wide dark blobs can have incompletely detected interiors under local thresholding.
- Bright defects, specular reflections, severe texture, and arbitrary uploaded images
  fall outside the synthetic generator's assumptions.
- Aggregate pixel F1 can hide rare, small, or class-specific failures; inspect individual rows.
- Search can get stuck from an infeasible incumbent if no single mutation crosses the floor.
- A 3% latency change can still be scheduler noise. Acceptance is exploratory, not proof.
- Conservative verification may reject a vendor build whose markers differ. Investigate
  its evidence instead of changing checks just to obtain a green status.
- The app is not a hardened multi-user upload service; it has no authentication or job queue.

## Security, privacy, and responsible use

The core app processes images locally to its server and requires no external AI service.
Do not use sensitive data in public demos. Restrict network access, use suitable TLS
for private deployments, keep secrets out of Git, and review any exported configuration.
The raw verifier includes local module paths; the checked-in artifact explicitly redacts
the personal path. See [responsible use](docs/RESPONSIBLE_USE.md).
